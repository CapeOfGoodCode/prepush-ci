## Context

`land` falls back to the comments of the pull request when neither the clone nor `origin` holds a result. For a comment that states a pass and names the head's tree, check and preflight, it asks `GET /repos/<owner>/<repo>/collaborators/<login>/permission` and counts the comment only on `admin` or `write`; an error counts as no (`land_comments.py`, `_writes`).

## Goals / Non-Goals

**Goals:** `land` lands from a cloud session on a pass in the result comment written by the same user; a comment counts only when its author has write access, as today; it keeps deciding as today wherever the author is not the token's user; an ignored pass is named with its reason.

**Non-Goals:** the reviewer check of `docs/ci/land.yml` (`land-workflow`); trusting any author whose write access `land` cannot show, in particular a comment of another user when the proxy refuses the permission path.

## Decisions

- **Only a writer's comment counts, as today; the change adds a second way to see a writer.** Robocop's invariant is that a trailer on the remote means the check passed on that tree, and `land` pushes without hooks, so the author of the pass must be someone who could have pushed anyway. The first draft of this change counted `author_association` `OWNER`, `MEMBER` and `COLLABORATOR` instead, which would let read-only members and read or triage collaborators vouch on every landing path, `land.yml` included (spec round 1, finding 1). It is dropped: no rule reads `author_association` now, so the question whether every writer shows as one of those values (round 1, finding 2) no longer arises.
- **The token's own user with push access is a writer.** `GET /user` names the user the token acts for; `GET /repos/<owner>/<repo>` with that token answers `permissions.push`, whether that user may push. When the comment's author is that login and `push` is `true`, the author has write access, shown with the same certainty as the permission lookup. It trusts nobody new: the person who could forge such a comment is the holder of a token that can push.
- **The token's user is asked first, the permission lookup after.** For the case #310 reports, the author is the token's user, so `land` lands without asking `collaborators/<login>/permission` at all, as the issue's first acceptance item asks, and sends no request the proxy is known to refuse. For any other author the permission lookup decides exactly as today, so the strict rule stays where GitHub serves it (Actions, a normal token): a read-only member's forged comment is still ignored there, and also through the proxy, where the lookup fails and a failed lookup is no.
- **The requests are lazy.** `GET /user` is sent once per run, and only for the first comment that matches the tree, check and preflight and has a known author that is not an App; `GET /repos/<owner>/<repo>` once, and only when a matching comment the walk reaches is by the token's user. A run without such a comment sends neither (new scenario "A comment that does not match sends no request"). Where the lookup works, a run sends at most these two requests more than today. The stub of `tests/integration/land_spec.py` answers both paths with 404 unless a spec sets them (its `respond` falls through to 404), which leaves every author to the permission lookup, so the existing specs of the comment route keep their outcomes and their assertions on requests: the four that assert no request at all (`test_a_result_ref_wins_over_a_comment`, `test_a_cache_that_is_off_reads_no_comment`, `test_without_a_token_no_request_is_sent_and_the_line_names_the_variable`, `test_without_a_repository_the_line_says_none_could_be_read_from_origin`) read no comment, and the others count only the comments listing (`api.asked(COMMENTS)`), the permission requests (`permission_asked_for()`) or the methods (`test_nothing_is_written_when_a_landing_succeeds_on_a_comment`, all `GET`), which a `/user` request does not change. Their total request counts do change: `test_only_matching_comments_are_asked_about`, for one, now also sends one `/user` request, for `alice`'s later matching comment; no existing spec counts all requests of a run that reads a matching comment. The scenario "Only matching comments are asked about" therefore keeps its main wording (no permission request for that user); `GET /user` names no user, so "no `/user` request for that user" could not be decided (spec round 2, finding 2), and the new scenario decides it for a run whose only comment does not match.
- **The walk has a requirement of its own, and the first comment that counts ends it.** "The comments are walked in order until one counts" says once what the other rules refer to as "the walk reaches": the comments in the order the listing gives them, page after page, the next page only while the last held 100 comments and none counted, and nothing sent or printed for a comment after the first that counts. Spec round 5 found the bound written twice and wrong: "before the first one that counts" left out the comment that counts, whose author must be asked about on the lookup path, and the token-user rule had no bound at all (finding 1). Now the write-access rule, the token-user rule and "An ignored pass is named" each say "the walk reaches", which includes the comment that counts; an ignored line is still only for one that does not count. For each matching comment of a known author that is not an App, the author is first compared with the token's user, then, unless that settles it, left to the permission lookup. `GET /user` is asked at the first such comment and its answer, or its failure, holds for the run; `GET /repos/<owner>/<repo>` is asked at the first such comment by the token's user and holds for the run; the permission is asked once per author. So a run sends at most one `/user` request, one repository request and one permission request per author, the token's user included when `push` is not `true` (round 5, finding 2), and the token user's pass lands through the proxy wherever it stands: a pass by another author before it (a reader's forgery, another user's session, a copy) is named and passed over, never a block (round 4, finding 1). A page that cannot be read ends the walk before its first comment, with no pass, as today: `authored_comments()` reads a page whole, so a `user` the API does not document makes the whole page undocumented, and no comment on it lands, is asked about or is named, even one before that `user`. The scenarios pin each state: the token user's pass first ("The proxy refuses the permission path", "Nothing after the token's user's pass is asked about"), after another author's ("The token's user after another author"), after a writer's that counts on the lookup ("A writer's comment before the token's user's": no repository request), twice with `push` `false` ("The repository is asked once"), behind a `/user` that fails or is undocumented ("The token's user cannot be read"), with no token-user comment ("The token's user is asked once"), a writer's pass before a reader's on the lookup path ("A writer's comment before a reader's"), a pass on a full first page ("A later page is not read") and an undocumented `user` after a writer's pass on the same page ("A page the API does not document ends the walk"). That a repository answer that is an error or undocumented leaves the token's user to the permission request, rather than to no, is pinned by a permission request in "A repository that cannot be read adds no reason" and a landing on `write` in "The repository answers without permissions".
- **A failure of either answer is no proof, and no reason on the `not landed:` line.** An error, an answer without a `login` string or without a `permissions.push` boolean, or `push` `false`, leaves the author to the permission lookup, which then answers as today. These requests are only a shortcut: their failure is not why a pass was not found, so the `not landed:` line keeps adding the first error of the comments listing or the permission lookup, as today. This narrows "A comment that cannot be read is not a pass", which on `main` says any error of the API adds its reason; the change modifies that requirement to name the two requests that add none, so the two rules cannot both apply (spec round 2, finding 1). That `GET /user` answers an error for an App's installation token (as on Actions) was not run here; nothing depends on it, since an error and a different login are handled alike.
- **The logins are compared exactly.** Both come from GitHub in its own spelling of the login (the comment's `user.login` and `/user`'s `login`), so equal strings are the same user; a comparison that ignores case would only add a way to be wrong.
- **Vouching across users through the proxy is not decided here.** A comment of another user, read through the proxy, does not count, as today. Whether sessions of different users should vouch for each other without a permission GitHub serves is trust only the owner can grant; this factory does not need it (its sessions share one user), so it is left out rather than asked, and would be a `proposal`.
- **The ignored pass is named on standard error, once per author.** Standard output keeps its one answer line, which scripts and `land.yml` read. The line is printed only for a comment that already states a pass and names this tree, check and preflight: other comments are noise and stay silent. The reasons are a fixed set: `a GitHub App`, `permission <value> is not admin or write`, `its permission cannot be read`. `<value>` is only ever `read` or `none`: a permission other than the four values the API documents (`admin`, `write`, `read`, `none`) is an answer it does not document, so it is "cannot be read", and nothing a server sends is printed verbatim there (round 1, finding 3). An App's comment gets the line too, since a factory may post the result comment as its App and would otherwise not learn why it was passed over. The `not landed:` line itself stays as for no pass, and a landing on a later comment prints the lines of the comments before it.
- **An author is known only by a plain login.** The login is printed in the line, so a `login` string that is empty or holds a character other than ASCII letters, digits, `-`, `_`, `[` and `]` (GitHub's logins are letters, digits and `-`; an App's ends in `[bot]`; a managed user's carries `_<shortcode>`) is taken as no login at all: a newline or a control character can never split or forge a line, and such a value is not sent in a request path either. A comment with `user` `null` or such a login is by an unknown author: it does not count, no request is sent about it, and one line `ignored a pass by an unknown author` stands for all of them, since there is nothing to tell them apart by (round 1, finding 3). A `user` that is not `null` and not an object with a string `login` and a string `type` stays what it is today, an answer the API does not document, which the `not landed:` line names (`test_a_comment_whose_author_has_no_login_is_an_answer_the_api_does_not_document` serves `user` `"alice"`); a `login` or `type` that is not a string joins it, where today `land` turned a number login into a login with `str()` and asked about it, and took a number `type` for a User's. The scenario "An author the API does not document" names each form the rule covers: `user` a string, an object without `login` or without `type` (undocumented today already), and a number `login` or `type` (the two that change); "A login that is not plain" names both forms of an unknown login, empty and with a newline (spec round 3, finding 3).
- **Requirements name each other by title.** ADDED requirements are appended at the end of the spec, so a reference by position ("next requirement", "the one after") points elsewhere once the change is archived (spec round 3, finding 1). The write-access requirement names "A comment of the token's own user counts without a lookup", and "A comment of the pull request is a pass when no result is found", whose "(the one after)" on `main` already points to "A comment names this tree, check and preflight" instead of the write-access rule, is modified to name both rules it refers to; its behavior and scenarios are unchanged.
- **The README says which errors the `not landed:` line names.** Its sentence "or when GitHub answers an error, the `not landed:` line says why" would be false for an error of `GET /user` or of the repository, which adds no reason, and the `readme` spec does not pin it; task 1.4 restates it (spec round 3, finding 2).
- **The rule and the lines are pure logic in `core/land.py`** (whether a login is plain, whether a permission is a writer's or an undocumented one, and the text of each ignored line), so `tests/unit` covers them; `land_comments.py` only reads and prints, and `github_api.py` gains `user()` (the login of `GET /user`) and `can_push()` (`permissions.push` of the repository), each raising `ApiError` on an error or an undocumented answer, like `permission()`.

## Acceptance of #310

- *Lands from a cloud session that did not run the check, on a pass in the result comment, without calling `collaborators/<login>/permission`*: met for a comment of the token's own user, the case #310 reports (scenario "The proxy refuses the permission path"). A comment of another user does not land through the proxy (Decisions, vouching across users).
- *The right to vouch is taken from `author_association`, or a better source*: deviation, the better source. `author_association` would let read-only members and read or triage collaborators vouch on every landing path, `land.yml` included (spec round 1, finding 1); `GET /user` with the repository's `permissions.push` shows write access as surely as the permission lookup, so the rule trusts nobody less than a writer and the question "what that trusts less than a write permission" has the answer: nothing.
- *A comment by an author who does not count is ignored, with a line naming the author and the reason*: met ("An ignored pass is named").
- *`land` still lands where the permission lookup works, as today*: met; such a run sends at most `GET /user` and `GET /repos/<owner>/<repo>` more ("The token's user cannot be read" lands on `write`; the existing scenarios of "Only a comment of someone with write access counts" keep their outcomes).
- *An integration spec runs `land` against a fake GitHub that refuses the permission path with 403 and serves the comments with `author_association`*: met. The proxy scenarios serve `author_association` as the proxy does, and "Another user's comment through the proxy" serves `bob`'s comment as `OWNER`: it must still not count, so a later change that reads the field fails a test (spec round 2, finding 3).
