# Design

## Context

Slice of #196, step 1, split from #197 ("Setting up the app" is the mockup). `report` already reads `PREPUSH_CI_APP_ID` and `PREPUSH_CI_APP_KEY` (the `report` spec); this change creates the app those two name. GitHub's manifest flow: the browser POSTs a manifest to GitHub, the user clicks "Create", GitHub redirects the browser to the manifest's `redirect_url` with a single-use `code`, and `POST /app-manifests/<code>/conversions` (no credentials) answers with the app's `id`, `slug`, `pem` and two secrets.

## Decisions

- **"No server of ours" means no hosted server.** The redirect needs an address the browser can reach, so the command listens on `127.0.0.1` on a free port for the one page and the one callback, and stops after the first valid callback or the timeout. Nothing is hosted, nothing outlives the command, and nothing but this machine can reach it.
- **The command prints the page's address and also opens it** with Python's `webbrowser`, so `BROWSER` decides and a machine without a browser (a cloud session) still has a link to copy. The test double for a browser is a `BROWSER` script.
- **`state` guards the callback.** A random `state` goes out with the manifest; a callback with another `state` or no `code` is answered 400 and ignored, and the command keeps waiting, so a stray request cannot end the setup or make it exchange a code of someone else's.
- **`--org <login>` picks where the app is created; without it, the signed-in account.** The alternative, asking GitHub whether the owner of `origin` is an organization, adds a request and a failure mode for a choice the user can make in one flag. The app is private (`public: false`): only its owner can install it, which is what a team's own reporting app needs.
- **The default name is `prepush-ci (<owner of origin>)`**, as in the #197 mockup; `--name` replaces it. GitHub allows 34 characters at most and names are unique, so a longer name or a taken one is for the user to choose; the command refuses a name of more than 34 characters before it opens anything.
- **The key goes to `<XDG_CONFIG_HOME or ~/.config>/prepush-ci/apps/<id>.pem`, mode 0600** in a directory of mode 0700 (the path of the #197 mockup). `~/.config` also on Windows, where the modes do not apply: one rule, and the key still lands outside every repository. An existing file is never overwritten. The command refuses before opening the browser when that directory lies inside the current worktree, so the key cannot be committed by accident (acceptance criterion: "its key is not in the repository").
- **The client secret and the webhook secret are dropped.** `report` needs neither (it signs a JSON Web Token with the key), and a secret that is not stored cannot leak. If one is needed later it can be made in the app's settings.
- **The environment variable holds the key's text, not a path.** `report` reads the key from `PREPUSH_CI_APP_KEY` (spec `report`); the command prints the variable's name, the id and the path of the file, and does not print the key.
- **A homepage, no webhook, no events.** GitHub requires the manifest's `url` (the app's homepage); it is prepush-ci's own address, `https://github.com/CapeOfGoodCode/prepush-ci` (the `Homepage` of `pyproject.toml`), so it is the same for every team and needs no owner or repository to be known. The manifest has no `hook_attributes` at all: GitHub requires a `url` inside it, the app has no server to point at, and without it the app has no webhook. `default_events` is empty, since the app only posts check runs.
- **`--timeout SECONDS` (default 300)** bounds the wait. GitHub's code lives an hour, but a user who walked away should get the terminal back; the flag exists so a test need not wait five minutes.
- **The owner is read as `report` reads it.** `app setup` takes the owner of `origin` from the same forms `report` accepts ("Where the result is posted": https, ssh and scp forms, `ssh.github.com`, userinfo ignored), so the two commands agree on who the owner is.
- **The manifest is JSON inside an HTML form**, so a `--name` with `"`, `<` or `&` is escaped for the page and reaches GitHub unchanged.
- **The README paragraph is not pinned by a requirement.** The `readme` spec checks drift, not prose (AGENTS.md), so this change only adds `app setup` to the reference, which the drift check covers. The paragraph the builder writes says only what a spec backs (AGENTS.md, "Docs say only what is pinned or run"): `app-setup` for the command, the key's path and the two variables; `report` ("The check run names what ran") for the check run's name, `prepush-ci / full`, which `--name` changes, and for the commit status `prepush-ci/full` when there is no app. A sentence about what a particular project's CI may skip is cut.

## Run it on GitHub

The conversion endpoint, as documented for the manifest flow: `POST /app-manifests/{code}/conversions` answers 201 with `id`, `slug`, `pem`, `client_secret` and `webhook_secret`. The form is posted to `https://github.com/settings/apps/new?state=<state>` (an organization: `https://github.com/organizations/<org>/settings/apps/new?state=<state>`), with one field `manifest` holding the JSON.

**Who runs it for real, and when.** The manifest flow needs a browser signed in as a person who owns the account, and a click on "Create"; no loop has that. Every test runs against a local double, so the builder's proof is the double's transcript, and the pull request says so. Before `turn:human`, the pull request carries `needs-human` with one question: the owner runs `prepush-ci app setup --org <a throwaway organization>` once, installs the app, runs `report` with the printed values, and reports what GitHub answered. A refusal of the manifest comes back as a `Bug` with GitHub's message; the double is then corrected to match.
