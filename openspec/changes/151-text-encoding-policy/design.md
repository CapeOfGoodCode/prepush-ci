# Design

## Context

Seven bugs of one class, all of the form "text meets a boundary and the module decided alone how to cross it". Reading the code at `d695b20`, five modules decide differently: `git.py` decodes git's output with the file system encoding (`os.fsdecode` rules, so it depends on the locale), `commit_msg_hook.py` decodes git's output with the locale and the message with strict UTF-8, `repo_config.py` reads files with strict UTF-8, `doctor_command.py` and `strip_command.py` decode with `replace`, and `cli.py` reconfigures standard output only. Two strings that mean the same (`oré` in the config, `oré` in `git remote`) differ under an ASCII locale, which is #146; a path held as file system text is written as UTF-8, which is #134. Fixing a command at a time cannot end this; one place has to own the crossing.

## Goals / Non-Goals

**Goals:** one place decides every crossing; the locale influences exactly one step; a non-UTF-8 byte in a file the tool edits survives; a file the tool must parse and cannot fails in one line, not a traceback; the suite runs the class.

**Non-Goals:** the output of the user's `check` and `preflight` (passed through as bytes of the child's own streams); `i18n.commitEncoding`; changing what any command prints or exits with when its input is fine.

## Tools run

git 2.39.5, uv 0.13.0, Python 3.13.16 (Linux), in `/tmp/encprobe/dé`, to settle what the policy must convert.

- `LC_ALL=C PYTHONUTF8=0 PYTHONCOERCECLOCALE=0 python -c …` reports: file system encoding `ascii`/`surrogateescape`; `sys.stdout.errors`, `sys.stdin.errors` `surrogateescape`; `sys.stderr.errors` `backslashreplace`. An argument `oré` arrives as `'or\udcc3\udca9'`. Under `LC_ALL=C.UTF-8` the same argument arrives as `'oré'`. So argument, environment and path strings are file system text, and file system text depends on the locale.
- `subprocess.run(["git", "--version", "oré"])` with the string `'oré'` (a real `é`) under the ASCII settings: `UnicodeEncodeError: 'ascii' codec can't encode character '\xe9'`. A `str` the tool built from git's UTF-8 bytes cannot be handed to a subprocess as it is.
- `os.fsdecode("oré".encode("utf-8"))` under the ASCII settings gives `'or\udcc3\udca9'`, and `os.fsencode` of that gives back `b'or\xc3\xa9'`: the round trip through bytes is exact, so a conversion through UTF-8 bytes loses nothing in either direction.
- `git remote`, `git rev-parse --show-toplevel` in `dé`, `git config --get` and the `refs/heads/fé` line git writes to a pre-push hook's standard input are the same UTF-8 bytes (`o r 303 251`) whatever the caller's locale. git does not follow Python's locale.
- `git interpret-trailers --in-place` on a message holding the byte `\351` (Latin-1 `é`) appends the trailer and leaves the byte as it was (`c a f 351 \n \n K : v \n`).

## Decisions

- **The tool's text is UTF-8 with `surrogateescape`, whatever the locale.** git, TOML and JSON are UTF-8; the locale only describes the operating system's strings. One text domain means a config value and a remote name compare equal (#146), and the `surrogateescape` half keeps a byte that is no UTF-8 alive (a path, a ref, a message) so that it can be written back unchanged. This replaces `git.py`'s file system decoding of #135.
- **The locale matters in two conversions only: `from_os` and `to_os`.** Arguments, environment values and `Path` objects are operating system strings; `from_os(s)` turns one into tool text (`os.fsencode`, then decode as above) and `to_os(text)` turns tool text into one (encode as above, then `os.fsdecode`), for a subprocess argument, an environment value or a `Path`. The probe above shows both directions are exact. Every other crossing takes bytes.
- **One module, `src/prepush_ci/text_io.py`, does every crossing that is not pure; `core/` stays free of I/O.** It offers: `decode`/`encode` (the domain, pure, unit-tested), `from_os`/`to_os`, `read_text(path)` (lossless, for a file the tool edits or only compares), `read_utf8(path)` (strict, raises `NotUtf8` naming the path, for a file the tool parses: TOML, JSON), `write_text(path, text, newline)`, a `run` that starts a subprocess with captured output and returns text, a `run_shell` that starts the user's `check` or `preflight` command through the shell, with the command converted by `to_os`, standard input closed and the output left to the child (`doctor` hands it a file to collect, as it does today), `stdin_text()` (reads the bytes of standard input) and `configure_streams()`. `git()` and `git_bytes()` of `git.py` build on it and keep their callers. The names are the builder's to adjust; the boundary, not the names, is the requirement.
- **The user's `check` and `preflight` are a crossing of their own: the command text goes to the shell, the output stays the child's.** `config.check` is tool text from UTF-8 TOML, and a `str` with `é` handed to a process under an ASCII locale raises `UnicodeEncodeError` (probe above; on `main`, `check = "echo é"` makes `run` end in a traceback under the `ascii` variant's environment). `run_shell` converts the command with `to_os` and nothing else: the child's output is not read or decoded by the tool, so "passes it through untouched" (Non-Goals) still holds. `checking.py`, `preflight.py` and `doctor_command.py` start their commands through it.
- **A test makes the rule hold for the next module.** It parses `src/prepush_ci/` except `text_io.py` and `core/` and fails on a call that decides an encoding: `read_text`, `write_text`, `open`, `.decode`, `.encode`, `os.fsdecode`, `os.fsencode`, `reconfigure`, `input`, any use of `sys.stdin` or `subprocess`, or a keyword `encoding`, `errors`, `text` or `universal_newlines`. The last four are the implicit crossings (a text stream decoded by the locale, a `str` handed to a process); `cli.py` and `init_command.py` pass `sys.stdin` today and move to `stdin_text()`. What a scan cannot see (`Path(text)`, `os.environ`, `sys.argv`) is held by the `ascii` variant alone, which is why that variant exists. The keyword `text` is banned on any call, so a helper of the tool cannot take a parameter of that name; that is intended, the builder names it otherwise. It is what turns the next sweep's finding into a failing test before the sweep. `core/` hashes with `.encode("utf-8")` (`run_cache.py`): that is a digest of the tool's own text, not a boundary, and `core/` is outside the scan.
- **A file the tool parses must be UTF-8 and says so; a file the tool edits keeps its bytes.** TOML and JSON are defined as UTF-8, so a Latin-1 `.prepush-ci.toml` is a config error in one line naming the file, the same way an invalid TOML file already is (`config`, "invalid TOML"). A hook manager's file (`.pre-commit-config.yaml`, a husky or lefthook file), a hook script and a commit message are not parsed: they are read, a block is replaced or a trailer added, and written back, with `surrogateescape` both ways, so the Latin-1 byte in a comment survives. Refusing those files would fail a repository for a byte the tool never looks at.
- **A commit message that is not UTF-8 gets its trailer, not a refusal.** The hook decides from the text (blank, template untouched) and git's `interpret-trailers` edits the file in place (probe above). Refusing would make the user pick another editor encoding to commit. #144 accepts either outcome; this one needs nothing from the user.
- **Standard output and error both replace what they cannot encode.** One rule for both streams (today output is set, error is `backslashreplace`); a report that quotes user text (#115) must print, and `?` is what output shows today. The replacement is `?` on output; error is not pinned beyond "does not raise".
- **Standard input is read as bytes and decoded in the domain.** git writes ref names to the pre-push hook as UTF-8 bytes, and an interactive `init` reads the user's answers that end up in a file written as UTF-8. Reading `sys.stdin` as text would decode with the locale.
- **The suite gets the variant through the fixtures, not a CI job.** `.github/` is reserved for the human and a loop cannot push a workflow. The `repo` fixture and the `cli` helper take a parameter `variant` (`utf8`, `ascii`); a test that uses either runs once per variant, and its id names the variant. In `ascii` the repository lives in a directory with a non-ASCII name (`dé`, below `tmp_path`) and every subprocess gets `LC_ALL=C PYTHONUTF8=0 PYTHONCOERCECLOCALE=0`, on every platform: on Windows the variables change nothing but the path still does, and that is the part Windows can break. The cost is the integration tier run twice; if it is too slow, the builder reports numbers and the human decides, no spec is dropped quietly.
- **Pre-commit is the one exception to the hostile variant.** `python -m pre_commit install` in `dé` under `LC_ALL=C PYTHONUTF8=0 PYTHONCOERCECLOCALE=0` ends in `UnicodeEncodeError` (pre-commit 4.6.2, exit 3): the spec cannot be met for a third-party program. Its processes (install, and the commits and pushes whose hooks it runs) get the outer locale; the repository path stays non-ASCII and the CLI's own processes stay hostile. Dropping pre-commit from the variant would leave its specs untested in `ascii` altogether; the exception costs only the tool as pre-commit starts it.
- **A spec starts the CLI by what it does, not how its source spells it.** The installed `prepush-ci` script and the demo's recording script start the CLI without `-m prepush_ci` in the spec's source, and a scan of the source misses them. How the builder detects it (a fixture or marker every such spec uses, with a check that fails on one without) is the builder's; the requirement is that these specs have both variants and none opts out.
- **Assertions in the variant compare what the variant prints.** In `ascii` a character output cannot encode comes out as `?`, so a spec that asserts on printed non-ASCII text asserts on that rendering; a helper of the fixture gives it. A spec that cannot run in a variant fails, it is not skipped (`AGENTS.md`, Testing).

## Risks / Trade-offs

- Every call site changes; the work is wide, the change per site small. The tasks cut it so that each commit passes alone.
- A path that exists on the file system but not as UTF-8 reaches output as `?`. Accepted: it is shown, not dropped, and a user can still act on the rest of the line.
- PR #142 (#134) and PR #147 (#144) change `install_command.py` and `commit_msg_hook.py` first; the builder rebases on them and moves their calls into the module as the first task, instead of replacing their tests.
