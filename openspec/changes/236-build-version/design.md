## Decisions

- **The installation record, not a development version.** A version such as `0.2.0.dev0` on `main` would need the version in `pyproject.toml` to change after every release and before the next, which is a change to the release procedure in `AGENTS.md` and still would not tell two builds of `main` apart. The record names the commit exactly, for every installer, with nothing to remember. The cost: an install from a package index, release or not, prints the bare version. A source tree with no installed distribution at all is not covered: it fails today and still does (not in #236).
- **Twelve characters of the commit.** The length the issue shows; enough to be unique in a repository of this size and short enough to read in a log. The record holds all 40; `git rev-parse` resolves the 12.
- **Only `vcs_info` is called git.** The record has one of three keys: `vcs_info` (a git URL, with `commit_id`), `dir_info` (a directory, editable or not) and `archive_info` (a file or an archive). A `vcs_info` that names a system other than `git`, or no commit, counts as a direct install: it is a build nobody can match to a release, which is all the suffix has to say.
- **`(direct install)` rather than a path or a URL.** The record can hold a path of the user's machine or a URL with a credential in it; a version line goes into reports and issues (this repository is public), so it never prints them.
- **A record that cannot be read counts as none.** Invalid JSON, a value that is not an object, or a missing file prints the bare version: `--version` is the first command anyone runs, and it never prints a traceback.
