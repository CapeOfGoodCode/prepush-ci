## Decisions

- **The asset is an animated SVG written by the script itself, not a terminal-recording tool's output.** asciinema, agg, vhs or svg-term would each be a new tool to install on every machine that re-records, and none is in the dev dependencies. A standard-library script has nothing to install, and SVG with CSS animation plays inline in a GitHub README (an `<img>`, no JavaScript) and on PyPI, where a GIF needs a second render step and is larger.
- **What is recorded is real, the timing is not.** Each command runs for real in the scratch repository and its output (standard output and standard error together, as a terminal shows them) and its exit status are captured. The cadence of the animation is a fixed schedule in the script (typing speed, a pause before the output, a pause after), so a slow machine cannot make the animation longer and the same recording does not depend on how fast git ran. Real waiting never appears.
- **The displayed command is the command that ran.** Git hooks and the typed lines both call `prepush-ci`; the script puts a one-line shim named `prepush-ci` first on `PATH` in the scratch environment that runs `sys.executable -m prepush_ci` (the way the tests start the CLI), so no line is rewritten between what the reader sees and what ran. The one exception is the install line, `uv tool install prepush-ci`: it needs the network and a release that does not exist yet, so it is typed and shown with no output and not run. The script marks it as the only step that is not run.
- **Long output is cut, not rewritten.** `init` prints a whole CI gate snippet. A step may keep its first lines (at most 6 per step) and then shows one line `…`; no line is edited or invented. A line wider than the screen is not cut: it fails the recording, naming the step, so the asset never shows a line the command did not print.
- **No machine path appears.** The scratch directory in the output is replaced with `.`. The home directory and the interpreter's path (the shim runs `sys.executable`, the recorder's venv under home) are not replaced but refused: if either is still in a step's output, the recording fails and names the step, so a traceback or a hint never reaches the asset (`AGENTS.md`: nothing private in public text). Replacing them would hide a failure the story should not have.
- **The opt-in is typed on the commit lines.** The commits are `PREPUSH_CI=full git commit …`, so the viewer sees the opt-in the README asks for ("Nothing happens until a machine opts in") on the line that needs it, and the displayed command is the whole command. Steps run as separate `sh -c` processes, so an `export` step would not reach the next one; a prefix does. The script removes every `PREPUSH_CI` it inherits so a maintainer's own setting cannot change the recording.
- **The recording is POSIX-only; the checks are not.** Steps are shell lines and run through `sh -c`, the shim is `#!/bin/sh`. Making them run under `cmd.exe` would mean a second dialect of every line in an animation that shows one. The specs that record are skipped on Windows with the reason, as `init_spec.py` and `install_spec.py` do; the specs that read the steps list or the asset run everywhere, so the command check, the duration limit and the README embed are still enforced on Windows.
- **Slow enough to follow: between 40 and 60 seconds.** The owner found the 29-second recording too fast and asked for about 45 seconds even if longer. The typing (per character) and the pause after each output both get slower, since the eye needs time at both; the target is about 45 seconds, the ceiling of 60 leaves the schedule room, and the floor of 40 keeps a later tightening from bringing the old pace back unseen. The figures stay in the script's schedule; the spec fixes only the range, measured from the asset.
- **A seam for the speed.** `--check-delay <seconds>` makes the fixture's `check.sh` sleep before it answers (default 0). The spec for "the duration does not depend on how long a command took" compares a 0 and a 2 second recording, not a 20 second one.
- **The first commit is `chore: set up prepush-ci`.** It adds only `.claude` and `.prepush-ci.toml`, and the animation should say so.
- **The screen is 92 columns by 12 rows and clears between acts.** It is wider than 80 so that the longest line of the story, the answer of `verify` with its 40-character sha (91 columns), is shown whole; 12 rows are as tall as the longest act needs. Scrolling would need a transform per step; clearing between acts (setup, commit, refused push, passing push) keeps each act on one screen and the SVG a fixed size. Each act is a list of steps in the script.
- **Typing is a stepped reveal.** A typed command is revealed by a clip animation with `steps(n)`, `n` the number of characters of the command, in a monospace font, so each frame shows one more character; nothing is hidden by a trick that a viewer sees as a fade.
- **The asset carries its own timeline as attributes.** The root has `data-duration` (the cycle in seconds, equal to the CSS `animation-duration`), and each step has `data-command`, `data-exit`, `data-start` and `data-end`. A test reads the timeline from the asset, so it measures what the viewer gets, not what the script intended.
- **A fixture repository with a deliberately failing check.** The scratch repository starts with one commit on `main` (a small `app.py` and a `check.sh` that fails until `greet()` ends with `!`), pushed to a bare remote. The failing push is the real hook refusing the real check; the fix is one `printf` redirected into `app.py`. The hook itself prints nothing when a check passes, so the fixture's `check.sh` prints one line on each outcome: `FAIL: greet() must end with !` when it fails and `ok: greet() ends with !` when it passes. The reader sees what to fix when it fails and sees the check pass when it does not.
- **The embed is specified in `demo`, not in `readme`.** A change to `readme` would have to be archived before #139's change to the same capability; the embed is one requirement, so it stays here.
- **The asset is committed, and nothing checks it is fresh.** Its output holds commit hashes, which differ in each recording; a freshness check would fail on every run. The recording script is tested end to end instead (into a temporary directory), so a CLI change that breaks a demo command fails the suite, and re-recording is a human or loop decision when the CLI's output changes.

## Tools run

Version: prepush-ci 0.0.0 (this repository at `main`), git 2.39.5, uv 0.13.0. A scratch directory with a bare remote, a `prepush-ci` shim first on `PATH`, no `PREPUSH_CI` exported (the commit lines carry it), and the fixture above, then:

- `prepush-ci init --non-interactive --check "sh check.sh"` prints `written: .prepush-ci.toml`, `installed: <scratch>/.git/prepush-ci/hooks`, `written: .claude/hooks/session-start.sh`, `written: .claude/settings.json`, then `CI gate (generic): add this to your CI` and 80 lines of snippet (hence the cut), exit 0.
- `git add .claude .prepush-ci.toml && PREPUSH_CI=full git commit -m "chore: set up prepush-ci"`, then `git log -1 --format=%B` prints the subject, an empty line and `Prepush-CI: full`.
- `git push origin feat/greeting` prints `FAIL: greet() must end with !`, `prepush-ci: the check failed (exit 1): sh check.sh` and `error: failed to push some refs to '../remote.git'`, exit 1.
- After `printf 'def greet(name):\n    return "Hello, " + name + "!"\n' > app.py` and `PREPUSH_CI=full git commit -am "fix: end the greeting with !"`, `git push origin feat/greeting` prints `ok: greet() ends with !` (from `check.sh`; the hook prints nothing on success) and `* [new branch]      feat/greeting -> feat/greeting`, exit 0.
- `prepush-ci verify HEAD` prints `verified: <sha> carries the trailer `Prepush-CI: full``, exit 0.

Not yet run: that GitHub plays the SVG inline (animated, through camo) and that PyPI does. The implementation pull request shows both on its branch before review (raw URL at the head commit), and the `Proof` of the pull request has the result.
