## Context

`land` (#292, #293) pushes the head of a pull request to the default branch when its tree has a pass; the ruleset of #294 lets only one bypass actor move that branch, and the experiment of #199 (T1, T2, T6) showed the built-in `GITHUB_TOKEN` cannot be that actor, so the workflow mints the token of the app that `app setup --land` creates. This change is the workflow users copy (`.github/` is reserved, so the file lives in `docs/ci/`, like the gate).

## Decisions

- **A capability of its own, `land-workflow`.** Rationale: `ci-gate` is the skip rule and `land` the command; a third file in `docs/ci/` with its own trust questions would make every later change to either conflict with this one.
- **The trigger is `pull_request_review` of type `submitted`, state `approved`.** Rationale: "an approved pull request" is the issue's words, and an approval is the one event that already means "a person looked". The expression `==` compares strings without regard to case, so the payload's `approved` and the API's `APPROVED` both match.
- **Only a reviewer with `admin` or `write` lands.** Rationale: on a public repository anyone can leave an `approved` review, and the event runs with the app's key in reach; `land` asks the same permission of a comment's author, so the rule is one rule. Read with `GET /repos/<repository>/collaborators/<reviewer>/permission` and the job's token; a failed call means no landing.
- **`decide` reads the pull request from the API when it runs: `GET /repos/<repository>/pulls/<number>` with the job's token (`head.sha`, `base.ref`, `draft`, `state`) and the review from `GET /repos/<repository>/pulls/<number>/reviews/<review id>` (`state`).** Rationale: `github.event` is the payload of the review, taken when it was submitted, and a re-run of the job reuses it (GitHub docs, *Re-running workflows and jobs*: the same `GITHUB_SHA` and `GITHUB_REF` of the original event). After a failed landing, a writer who pushed a new head, retargeted the pull request, made it a draft or closed it, or a reviewer who dismissed the approval, could click "Re-run" and have `decide` compare two old values that still match. The payload gives `decide` only what cannot change (the number, the reviewer, the id and the commit of the review); the default branch also comes from it, and a rename since then makes the base differ, so the answer is `land=false`, never a landing. A failed call means no landing.
- **The approved commit must be the head now (`review.commit_id` equals `head.sha` of the API).** Rationale: without it a push after the approval would land code nobody reviewed. A push between the read and `land`'s own fetch of `refs/pull/<n>/head` is not closed (they are seconds apart in one run, it needs write access, and what lands still has a pass for its tree); closing it takes a `--sha` argument on `land`, a different change.
- **Only a pull request against the default branch lands (`base.ref` of the API equals the default branch).** Rationale: `land` pushes the head to the default branch and never reads the pull request; a pull request based on another branch carries that branch's commits, which would land with it and without their own approval (a stacked pull request, or one against `release/1.x`). The rule is in `decide`, where a scenario can run it.
- **A draft or a closed pull request never lands (`draft` and `state` of the API, in `decide`), and neither does an approval that is no longer one (`state` of the review must be `APPROVED`).** Rationale: GitHub accepts an approving review on a draft, but a draft says "not ready"; a pull request closed without merging was dropped on purpose; a dismissed approval was withdrawn, and `land` never reads reviews, so only `decide` can stop a re-run on the payload's `approved`. The approval is ignored without a trace; once the draft is ready, the author asks for a new approval, as after any push.
- **A pull request from a fork never lands.** Rationale: the event gives a fork's run no secrets, and its `preflight` is the code we least want to run with the app's token. The `if:` says so, silently.
- **No `concurrency` group: every approval gets its own run, and `land`'s fast-forward push is the order.** Rationale: "only landing is ordered" (#199) holds without a lock, because `land` pushes without `--force` and `origin` accepts one of two heads that do not contain each other; the other gets the line of a moved branch (`land`, "A refused push is reported, never forced"), which the job comments. A group would cost an approval: GitHub keeps one pending run per group and cancels the older of two that wait ("by default only one run can be pending in a concurrency group—any additional pending runs cancel the previous one", GitHub docs, *Concurrency*), whatever `cancel-in-progress` says; with `cancel-in-progress: true` it would also cancel a landing under way. The opt-in queue of the same page (`concurrency.queue: max`, up to 100 pending runs, in order) is the alternative this turns down: it orders nothing that `land` does not already order, because `land` never rebases, so the second head is refused as moved either way and a queue only delays that refusal; it also makes every `preflight` wait for the one in front, and a run that waits widens the gap between the read of `decide` and the landing. The price of no group is that two `preflight`s may run at the same time. Nothing waits, so `decide` and `land`'s fetch of `refs/pull/<n>/head` are seconds apart (the line on the head above).
- **The token comes from `actions/create-github-app-token`, pinned to the commit of v3.3.0 (`64ab729a6294000f5aa4a4bc0b73d1f32bc45510`), with `app-id`.** Rationale: it is the maintained way to turn app id and key into an installation token; `app-id` is the number `app setup` prints (the newer `client-id` is a string the command does not print), at the cost of a deprecation notice in the log. The names `PREPUSH_CI_APP_ID` (variable) and `PREPUSH_CI_APP_KEY` (secret) are the ones `app setup` already prints for `report`.
- **The checkout is of the default branch, with `fetch-depth: 0` and the app token kept.** Rationale: `land` checks an ancestry and pushes through `origin`; a shallow clone cannot tell, and `origin` needs the credential. It is the default branch, not the pull request's merge commit, so the clone holds none of the pull request's files; `land` reads the head itself.
- **`pipx run prepush-ci`, as the action does.** Rationale: `pipx` is on the hosted runners and the action already defaults to it; the file's comment tells the user to pin a version.
- **A refusal is one new comment, posted with the job's `GITHUB_TOKEN` (`pull-requests: write`), and the run stays green.** Rationale: the app's token stays in the two steps that need it (checkout, `land`); a refusal is a normal outcome, told where the author looks, and a red run nobody reads adds nothing. A crash of the step (no output line) is commented too, with the run's link. The fixed text tells each kind of refusal what to do, because the line cannot be parsed for a cause and the answers differ: for a moved branch or a missing pass, rebase onto the default branch and push, so that the pre-push hook checks the new tree, and ask for a new approval; for a missing variable or tool, change the workflow (a rebase cannot help). The `land` step passes only the job's token, so a config with `require_env` or a `preflight` that runs a tool the runner lacks refuses on every approval until the user adds the variables to the step's `env:` or the tool to the job; the header of the file says so.
- **The line goes into a code block with its backticks removed.** Rationale: the line is `land`'s own text, but its refusal reason can quote the remote's message; removing backticks keeps it a single block, and `land` already promises it never holds a file's content.
- **After a rebase and a push, the author asks for a new approval.** Rationale: the old approval is on another commit and does not match the head (above); the comment says so.
- **The key is stated as it is, not closed: a repository secret that every writer can read.** Rationale: the closing designs (the secret in an environment that only runs on the default branch, and a `workflow_run` workflow, which GitHub runs from the default branch's copy, that rereads the review, the reviewer's permission and the head from the API) cannot be tried from here, double the files, and decide the example's shape on the strength of platform behavior nobody has run; they are a later change if the owner wants them after the first real landing (#296). The Risks and the header of the file say what the example costs.

## Not verified here

The loop's token cannot run a workflow or create an app, so `docs/ci/land.yml` has not run on GitHub: the specs parse it and run its scripts with stubs. Four calls are taken from GitHub's documentation and the first real run, the owner's in #296, confirms them: `GET /repos/<repository>/collaborators/<login>/permission` and `GET /repos/<repository>/pulls/<number>` and `.../reviews/<review id>` answer with the job's `GITHUB_TOKEN` (the first checked here only with a user token: `{"permission":"admin","role_name":"admin"}`, `gh` 2.102.0), and `create-github-app-token` yields a token that `git push` accepts as the ruleset's bypass actor (T1 of #199 did it with an app's token).

## Risks

- **Anyone who can push to the repository can read the app's key, and the rules are theirs to change.** `PREPUSH_CI_APP_KEY` is a repository secret; GitHub hands it to every `push` and same-repository `pull_request` run, so a writer who pushes a branch with a workflow of their own can read it, with no approval and no `land`. The app is the ruleset's only bypass actor (`contents: write`, `workflows: write`), so with the key stored, "only the app moves the default branch" holds against people who cannot write, not against those who can. On `pull_request_review`, GitHub also runs `land.yml` as it stands in the pull request's merge commit, so `decide` is the copy in the pull request under review, and its checks (permission, head, base, draft) bind only an honest author. What the ruleset and the workflow add is the order and the pass check for everyone else; against a writer who means harm they add nothing. The header of the file and the README say so, and the cost is accepted by whoever stores `PREPUSH_CI_APP_KEY`, after reading the header and the README: each user, and for this repository the owner in #296, whose acceptance criteria name it.
- `land` runs the `preflight` of the pull request, and the checkout holds the app's token. A malicious `preflight` approved by a writer can use it: move the default branch to any fast-forward, or change workflow files. That is the power of landing; the answer is the reviewer's, who approves the code of the config too, and the header of the file says so. The default app (`app setup` without `--land`) is not affected.
- The example needs a release of `prepush-ci` that has `land`.
