## Context

`land` finds a pass by the key `<tree>-<config>` as the pre-push hook does. A session that cannot push refs leaves one trace of its run: the comment of "The comment is the Markdown of report" (`post-push-hook`), which holds a `Tree` row and a `Check` row in a table. The comment is text anyone with a GitHub account may write on a public repository, so what makes it a pass is who wrote it and what it says.

## Decisions

- **Only comments of users with write access count; a comment of an App never does.** `GET /repos/<owner>/<repo>/collaborators/<login>/permission` answers `permission`; `admin` and `write` count, anything else (and any failure to read it) does not. Rationale: the trailer is the trust of a session that has write access; a comment of someone who cannot push must not be worth more. The author's login comes from the comment's `user.login`; one lookup per distinct author, only for comments that already match the rest. A comment whose `user.type` is `Bot` is dropped before any lookup. Why: the endpoint answers `none` for an App's bot user even when the App pushes here (checked: `collaborators/cogc-factory[bot]/permission` answers `"permission":"none"`, `"push":false`, `"type":"Bot"`), so a bot cannot be told apart from a stranger by permission, and `author_association` says `CONTRIBUTOR` for it. Who posts the comment of a cloud session: the post-push hook, with the credentials the session has (`GITHUB_TOKEN`, `GH_TOKEN`, or the proxy of a Claude Code cloud session), so the author is whoever those credentials are. The experiment of #199 (T8) shows that session's git pushes arrive as its user; nothing in it shows who the proxy makes the author of a REST comment. A session whose credentials are a user's gets its comment counted; one whose credentials are an App installation token does not, and `land` then checks again. Cost: no landing on a comment from an App, and a second full check where one was avoidable. Rationale: failing safe costs time, admitting a bot costs the trust of the trailer. Admitting chosen Apps (a config key) is a later change if the owner finds the cloud sessions post as an App.
- **Match first, ask the API last.** The comment must start with the default marker, say a pass, and name this tree, this check and this preflight before any permission is looked up. Rationale: a pull request with a hundred comments costs one lookup per matching author, not per comment.
- **Any matching comment of a writer is enough.** Rationale: the hook keeps one comment per check, but an older comment of another commit with the same tree is as good a statement as the newest one; the tree decides, not the order.
- **The comment must name the tree in full, the `Check` and the `Preflight` command as committed in the head, and not what the preflight printed.** The ref's key holds the output of the preflight, which the hook computes in the session; a comment is the Markdown of `report`, which holds no output, so it cannot attest it. Chosen: a comment counts whatever the preflight printed. Rationale: a preflight usually prints tool versions; refusing every comment when the config has one would void the feature for those repositories, and the same comment already is the session's statement that it checked, like the trailer. Cost: a tool upgraded between the session's check and the landing goes unseen when the pass is a comment; a result ref does not have this gap, and it wins.
- **The `Check` and `Preflight` cells are compared with what `report` writes, cell for cell.** The hook posts only for a pass of the committed config (next decision), so the cells of its comment can differ from the committed values only in how `report` renders them: code span with white space merged and a fence longer than the longest backtick run (`code_span`), and each `|` written `\|` (`_table`). The expected cell is made with the same rendering, never by stripping the comment's cell. Rationale: a stripped comparison refuses a real pass for `check = "sh scripts/ci | tee ci.log"`.
- **The hook's comment attests the config that ran: the result commit records a digest of it, and the hook posts only for a pass of the committed config.** `report` fills `Check` and `Preflight` from the config committed in `HEAD`, and the pre-push hook runs the `check` of the worktree config, which can be an ignored file that differs (`run-cache`, "Changed check command"). Without more, a pass of `true` would be posted as a pass of `scripts/ci`, and `land` would match it cell for cell. So the message of the result commit gains `config <digest>` (`check`, `preflight`, `require_env`, `require_up_to_date`: the key's inputs less the preflight's output), and the post-push hook counts only the refs whose digest is that of the committed config. The comment then says what ran, `land` can compare it, and `require_env` and `require_up_to_date` are attested as well, though the comment does not show them. Rationale: it keeps the criterion of #293 ("the check named in it is the configured check") true for hook comments, at the price of two small deltas in `run-cache` and `post-push-hook`. Cost: a ref recorded before this change has no digest, so its push gets no comment (refs expire after 30 days, and the next push records one). A comment written by hand is the writer's word, like the trailer; the cell comparison catches only a stale or careless one.
- **The marker is the default one, `<!-- prepush-ci:prepush-ci / full -->`.** Rationale: the config has no name of the check; the comment of the hook uses the default name, and another name is another check.
- **A pass is the line `### prepush-ci / full: Passed` or `### prepush-ci / full: <n> passed, 0 failed, <m> skipped`, and no line `### Failures`.** The title line of a failed result with counts is `### prepush-ci / full: Failed (<counts>)` after this change; before it, a failed result with zero failed cases (a mypy error only) looked like a pass. The title of the check run itself stays the bare counts. Rationale: a comment states its result in one way, so `land` does not guess from the counts.
- **The result ref wins; the comment is read only when the ref is missing.** Rationale: the ref is the stronger statement and needs no API; the cost of reading comments is paid only by sessions that cannot push refs.
- **The token and the repository are found as `report` finds them.** `GITHUB_TOKEN`, else `GH_TOKEN`; the repository from `origin`, else `GITHUB_REPOSITORY`; `GITHUB_API_URL` for the address. Rationale: one rule for every command that talks to GitHub. The token is sent only to that address and never printed.
- **A comment that cannot be read is not a pass, and the line says why.** No token, an unreadable repository, an API error and a reply the API does not document each end in `not landed:` with the reason appended to the "no pass" line. Rationale: a landing must not fail silently into a second full check that the user thinks is a missing result.
- **Comments are read after the preflight, with the other lookups.** Rationale: the key needs the preflight's output, and every refusal that needs no command of the head already came first.
- **No comment is written and no ref is made from one.** Rationale: `land` pushes one ref only, the default branch.
